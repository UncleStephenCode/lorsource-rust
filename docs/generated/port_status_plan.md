## Второй раунд аудита: темы/форум, комментарии, реакции, разделы (ЗАВЕРШЕНО, всё протестировано)

### Найденные и исправленные несоответствия
1. ~~Окно удаления темы автором было 3 часа вместо 3 дней~~ — `TOPIC_DELETE_WINDOW_HOURS` был буквально в 24 раза меньше `GroupPermissionService.DeletePeriod`; комментарий в коде ошибочно утверждал соответствие. Поправлено на 72.
2. ~~`has_replies` считал удалённые ответы~~ — комментарий с единственным (уже удалённым) ответом навсегда терял право редактирования/удаления автором; добавлен `AND NOT r.deleted`, как в `CommentDao.getRepliesCount`.
3. ~~Штраф score при удалении коммента не обнулялся для frozen-автора~~ — добавлена проверка `frozen_until`, как в `DeleteService.doDeleteCommentWithScore`.
4. ~~Не было проверки "тема просрочена" при редактировании/удалении/восстановлении коммента~~ — добавлен `is_topic_expired` (формула точно как в `TopicDao`: `!sticky && COALESCE(commitdate,postdate) < now()-expire`), с разной строгостью для автора/модератора/восстановления, как в `TopicPermissionService`.
5. ~~Постинг комментария почти не валидировался~~ — не было ни лимита длины (8192 симв.), ни flood-protection (интервал между сообщениями по score, как в `FloodProtector.AddComment`), ни проверки состояния темы (deleted/draft/expired) и postscore-ограничений (registered-only/moderators-only/no-comments/hide-comments/score-loss/open-warnings) — реализован полный `check_comment_posting_allowed`, зеркалящий `TopicPermissionService.isCommentsAllowedByUser`/`getPostscore`.
6. ~~Каскадное удаление веток комментариев модератором отсутствовало полностью~~ — реализован `delete_replys` с затухающим по глубине штрафом (`DeleteReasons.replyBonusAndReason`: -2/-1/0 в терминах Java, что эквивалентно +2/+1/0 в знаковой конвенции этого порта — см. п.9), пропуском уведомлений при просроченной теме.
7. ~~Sticky-темы не учитывались в expired для реакций/голосования~~ — `check_reaction_allowed`/`vote()` считали `expired` от `postdate` без учёта `sticky`, из-за чего sticky-темы ошибочно "просрочивались"; плюс не использовался `COALESCE(commitdate,postdate)` для премодерируемых разделов. Исправлено на точную формулу `TopicDao`.
8. ~~Реакции не проверяли frozen-пользователя и `isCommentsHidden`~~ — добавлены обе проверки в `check_reaction_allowed`, как в `ReactionService.allowInteract`.
9. **КРИТИЧЕСКИЙ БАГ, найденный при тестировании (не из аудита)**: `reactions_log` был создан с придуманной схемой (`userid`/`msgid`/`set_value`/`action_date`, все NOT NULL без дефолта) вперемешку с реальными колонками (`origin_user`/`topic_id`/`comment_id`/`set_date`/`reaction`, точно как в Java `2023-09-23-reactions-log.xml`). Код никогда не заполнял придуманные колонки — то есть **вообще ни одна реакция не сохранялась ни разу**, любая попытка падала 500 на NOT NULL constraint. Исправлено миграцией `0015_fix_reactions_log_schema.sql` (дроп придуманных колонок, NOT NULL на настоящих). Обнаружен только благодаря живому end-to-end тесту через Docker — статический аудит кода это не поймал бы.
10. ~~GET-просмотр реакций не проверял видимость~~ — `reactions_get` не проверял deleted/isCommentsHidden для комментариев и не гонял `checkView` для тем; добавлено (см. новый `check_topic_viewable` в topics.rs).
11. ~~Роль corrector не подключена к commit новостей~~ — добавлено поле `corrector` в `StUserSummary`/`CurrentUser`; `commit_topic`/`commit_topic_form` теперь разрешают corrector (кроме подтверждения своей же темы), как в `EditTopicChecker.checkCommit`. `uncommit`/`move` проверены — в Java они действительно moderator-only (другой контроллер), изменений не требуют.
12. ~~Автор мог редактировать подтверждённую премодерированную тему в течение 14 дней~~ — на самом деле после `commited=true` в непремодерируемых-Статьях разделах право редактирования пропадает **навсегда**; для Статей дедлайн отсчитывается от `commitDate`, а не `postdate`. Реализовано точно по `EditTopicChecker.checkEditByAuthor`.
13. ~~Восстановление удалённой темы не проверяло срок давности~~ — обычный модератор мог восстановить просроченную тему когда угодно; теперь для просроченной темы разрешено только в течение 14 дней с момента удаления, иначе только администратор (`GroupPermissionService.isUndeletable`).
14. ~~Доступ к удалённым темам в листингах был moderator-only~~ — на самом деле это score-based право (`canViewAllDeletedTopics`: score≥50, без исключения для модераторов буквально по коду Java) для списков групп, и отдельное (`allowViewAllDeletedComments`: score≥200, с исключением для модераторов, плюс scoreLoss/postscore-условия) для `?deleted=` на странице темы. Реализованы оба как разные функции с разными порогами.
15. ~~Обычный модератор мог удалить любую подтверждённую премодерированную тему~~ — по `GroupPermissionService.isDeletableByModerator` это разрешено только в течение 1 месяца с момента публикации, дальше — только администратор.

Все 15 пунктов проверены live-тестами (позитивные и негативные сценарии) через Docker-стек, тестовые данные подчищены после каждого прогона.

- В трекере нет модераторской боковой панели (новые/frozen/blocked юзеры, счётчик неподтверждённых).
- Поиск: нет точного поиска по дате, границы интервала `gt` vs `gte` не совпадают, разница в весах релевантности — мелкие детали.
- "Недавно заблокирован" grace-period захардкожен в 90 дней — не подтверждено сравнение с реальной константой Java.
- Пагинация уведомлений не группирует подряд идущие события одного типа/темы (WARNING и REACTION события теперь создаются штатно, см. P1 пп.2,53 — группировка всё равно не реализована).

## ЗАВЕРШЕНО в этой сессии

### Security (критические уязвимости, все закрыты и протестированы)
- **CSRF защита отсутствовала полностью** — у Java есть глобальный `CSRFHandlerInterceptor`, применяемый к каждому POST (double-submit cookie `CSRF_TOKEN` + скрытое поле `csrf`), в Rust-порте не было ни middleware, ни проверки, ни единого поля в формах (хотя фронтенд-JS, скопированный из оригинала, уже ожидал cookie `CSRF_TOKEN` и поле `csrf` - `getCsrf()` в `static/js/add-form.js` был мёртвым кодом). Реализован `src/csrf.rs`: глобальный middleware ставит `CSRF_TOKEN` (не-`HttpOnly`, как и в оригинале - иначе JS-инжектируемая форма логаута в `base.html` не смогла бы прочитать токен), сверяет поле `csrf` на каждом POST с `application/x-www-form-urlencoded`-телом (совпадает с cookie), 403 при несовпадении/отсутствии. Добавлено скрытое поле `csrf` во **все** ~30 форм на сайте (шаблоны + инлайн-HTML в обработчиках). Найден и закрыт обходной путь собственного дизайна: bodyless POST без `Content-Type` (например `fetch(url,{method:"POST"})`) изначально проскакивал проверку, потому что она была условна на `Content-Type: ...-urlencoded`; исправлено на "проверять всегда, кроме multipart". Сознательное упрощение: multipart-загрузка (`/addphoto.jsp`) не защищена полем `csrf` (не буферизуем/не парсим multipart-тело в middleware) - остаётся на `SameSite=Lax` сессионной куки.
- **Cookie `Secure` не выставлялся никогда** — `lor_session`/`lor_user`/`lor_theme` (и новый `CSRF_TOKEN`) ставились без `Secure` даже по HTTPS. Добавлен `security::is_secure_request()` (тот же `X-Forwarded-Proto`-чек, что уже был в `security_headers`/`csrf`) и `.secure(is_secure)` на все куки, выставляемые при логине/активации/CSRF.
- `CSRF_TOKEN` из входящей cookie валидируется по алфавиту (`generate_token`'s base64url) перед тем, как попасть в raw-HTML `format!`-формы (не все формы в проекте — Askama-шаблоны, которые эскейпят `{{ }}` сами); невалидное значение (например HTML-мета-символы, если кука была подставлена вручную) отбрасывается и перевыпускается новый токен - защита от отражённой инъекции через это единственное неэскейпленное поле.

### Итог сессии
Полный порт функционала завершён (все пункты «Крупное»/«Среднее» закрыты, кроме двух принятых внешних ограничений: GeoIP без реальной БД, legacy Jasypt-хеши без прод-дампа). Отдельный security-проход этой сессии нашёл и закрыл: полное отсутствие CSRF-защиты (при уже готовом, но неиспользуемом фронтенд-JS под неё) и отсутствие `Secure` на всех cookie. Все изменения протестированы end-to-end через живой Docker-стек (позитивные и негативные сценарии), тестовые данные каждый раз подчищены.
- delete/undelete/edit комментариев и тем — не было проверки авторизации вообще
- email hijack — смена email без пароля и подтверждения, теперь через `oldpass` + `new_email`/activation
- `/people/{nick}/profile/wipe` — деструктивный GET без подтверждения → модератор-only confirmation-страница
- `/delip.jsp` — делал противоположное действие (unban вместо mass-delete+ban)
- `/people/{nick}/reactions`, `/people/{nick}/remarks` — публичный доступ без авторизации; remarks вдобавок показывал не то направление
- История правок — читалась анонимусами
- `user_remarks` — схема не совпадала с Java (userid/who/remark vs id/user_id/ref_user_id/remark_text)
- 3 stored-XSS (профиль userinfo `|safe`, autolink regex не исключал кавычку, markdown пропускал сырой HTML) + 1 reflected-XSS (`filter` в notifications) — закрыты через `ammonia` (аналог jsoup Safelist.relaxed() из оригинала) как универсальный финальный фильтр + regex-фикс + allow-list на filter
- SQL injection — аудит не нашёл ни одного случая (везде параметризованные запросы)

### Функциональность
- Корневая причина ~90% первоначальных 404 — весь роутинг был в синтаксисе axum 0.8 (`{param}`) при закреплённой версии axum 0.7 (нужен `:param`) — все параметризованные маршруты не матчились вообще
- Система нотификаций — реализована с нуля (генерация REPLY/WATCH событий, счётчик, HTML-страница, mark-as-read, click-through, yandex-tableau), плюс починен enum `event_type` (был с придуманными значениями)
- Редиректы после действий с комментами/темами — `?cid=N` как в оригинале
- Premoderation + черновики + лимит длины сообщения при создании тем — раньше отсутствовало полностью
- Reactions — GET показывает HTML/редиректит, POST редиректит (не JSON), JSON только на `/aj`; починен краш (`groups.expire` → `sections.expire`)
- Тема оформления теперь рендерится на сервере (middleware), а не только через JS; подключена syntax highlighting для code-блоков
- Sequence для `tags_values` синхронизирован; `s_msgid`/`s_uid` уже были ок
- `/memories.jsp` — был сломан (отсутствовал unique constraint под ON CONFLICT)
